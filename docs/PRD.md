## 1. 产品定义

面向 UW–Madison 全部学生，包括第一次找科研的学生。通过低门槛输入、跨院系研究探索、通俗解释、候选比较和正确的联系入口，帮助学生形成自己的选择，并完成邮件准备和批量发送。

### 1.1 第一版必须做到

1. 有独立介绍首页，点击 **Get Started** 后进入工具。
2. 不要求先上传简历、列技能或填写完整个人档案；一句兴趣描述即可开始。
3. 全校公开信息均在搜索范围内，允许跨院系，不把“CS 专业”当作只能检索 CS 院系的限制。
4. 根据兴趣清晰程度呈现方向、教授或多个兴趣组。
5. 让学生读懂研究，能查看来源、比较对象并确定下一步。
6. 条件标签区分支持、不支持、未说明；不能把未知变成肯定答案。
7. 同时支持快速批量草稿、可选问题个性化和编辑预览。
8. 支持用户授权邮箱后的真实批量发送，并准确保存逐封状态。
9. （暂时先不做，第二阶段再考虑：可以监控发的邮件是否收到了回复，若回复则提醒用户）

### 1.2 核心原则

- 用户明确表达的未来兴趣优先于简历中的历史经历。
- 注意关键词：比如用户是本科生，在教授的相关信息中寻找是否有“不收本科生”-明确拒绝或者“收本科生”-明确机会或者没有的话-不确定
- 推荐表示“值得你了解”，不等于“教授有空缺”“你满足所有条件”或“会被录取”。
- 不以缺少科研经验或无法填写技能为由阻止探索。
- 每一步都尽量先提供价值，再让用户补充信息。
- AI 解释服务于理解和比较；关键事实要有出处。
- 联系行动服从公开渠道要求，不把所有对象默认导向 cold email。
- 批量是集中处理多封独立邮件，不是把多位教授放在同一封邮件里。

### 1.3 已确认需求与建议默认值

本文“必须”对应用户已确定的范围或保证其正确运行的要求。“建议默认”是为形成可执行方案提出的设计选择，并不冒充用户已确认。

| 项目 | 建议默认 | 状态 |
|---|---|---|
| 交互语言 | 界面英语优先；支持中英文输入；研究解释跟随用户语言；邮件默认英语 | 待交互评审确认 |
| 初始结果 | 首屏呈现约 6 个可信候选，其余按需展开；不以数量填充无关结果 | 可用性测试后调整 |
| 比较数量 | 2–3 位为默认体验，超过时提示分批比较 | 待原型验证 |
| 简历格式 | 文本 PDF、DOCX；建议单文件不超过 10 MB | 待解析方案验证 |
| 邮箱提供方 | 优先验证 UW Microsoft 365，不承诺第一版接入所有邮箱（必须是UW Microsoft 365才能使用这个工具，通过给学生邮箱发验证码来确定身份） | 必须实测 |
| 保存范围 | 访客在当前浏览器继续；跨设备同步不作为第一版完成条件 | 待存储方案细化 |
| 招募与入口复查 | 联系前对超过建议 7 天未核查的入口与招募说明重新检查 | 频率待成本与可用性验证 |

不得因上述建议默认值尚未确认，删除已经确认的跨院系探索或批量发送功能。

## 2. 页面结构与导航

以下为页面职责，不锁定框架、组件库或具体 URL。

| 页面 | 主要内容 | 主要动作 | 返回时保留 |
|---|---|---|---|
| P01 介绍首页 | 价值说明、产品示意、工作方式、FAQ | Get Started；了解工作方式 | 已有工作区入口 |
| P02 探索输入 | 自然语言、可选简历、可展开背景 | 开始探索 | 原始输入、已确认背景 |
| P03 探索结果 | 方向组或教授列表、筛选、来源覆盖说明 | 选择方向、详情、收藏、加入比较 | 搜索、筛选、位置 |
| P04 教授／实验室详情 | 通俗说明、研究例子、来源、参与条件、下一步 | 原始主页、比较、准备联系、申请入口 | 候选选择 |
| P05 比较 | 同维度对照 2–3 个候选 | 保留候选、查看详情、准备联系 | 比较对象 |
| P06 我的候选 | 收藏、选择理由、公开联系渠道 | 准备邮件或打开申请入口 | 候选和个人备注 |
| P07 邮件工作区 | 多封草稿、编辑、个性化问题、附件 | 生成、补充细节、预览发送 | 每封邮件独立内容 |
| P08 发送预览 | 发件邮箱、收件人、主题、正文、附件、勾选 | 连接邮箱；确认发送所选邮件 | 草稿和勾选 |
| P09 联系记录 | 逐封状态、批次、已发送内容、手动进度 | 查看、处理失败、回看研究 | 原始发送记录 |

工具全局导航围绕“探索／我的候选／邮件”组织。介绍首页和工具保持一致的名称与视觉，点击品牌可以回首页。探索和比较不要求先连接邮箱。

主路径：**P01 → P02 → P03 → P04 → P05／P06 → P07 → P08 → P09**。

这不是强制向导。用户可以跳过比较直接准备联系，也可以直接搜索已知教授；表单或项目申请对象从详情进入公开入口，不必经过邮件页面。

## 3. 介绍首页与首次进入

### FR-01 介绍首页（P0；对应 BR-01）

首页承担说明与引导作用，不复制工具的所有输入和筛选。

建议内容顺序：

1. 产品名称与简短导航。
2. 首屏标题：说明帮助 UW 本科生探索第一段科研；主按钮固定为 **Get Started**。
3. 一句价值说明：从兴趣开始，看懂研究，找到值得联系的人。
4. 一张真实产品预览或明确标注的示意，优先呈现“通俗研究说明＋推荐依据”。
5. 三步工作方式：表达兴趣、理解与比较、采取下一步。
6. 主要能力：跨院系探索、可追溯信息、邮件生成与批量发送。
7. 简短 FAQ：需要简历吗、没有经验能用吗、是否知道名额、如何使用邮箱。
8. 页尾 Get Started 和基本数据处理说明。

要求：

- Get Started 直接进入工具的兴趣输入；首次探索不被注册表单阻断。
- 已有未完成工作时显示“继续探索”，也允许开始新搜索。
- 不使用虚构用户评价、用户数量、回复率、名校合作或学校官方背书。
- 参考用户截图中的页面层次，不复制其商标、图片或未经核实的产品承诺。
- 首页不展示模型名称、数据管道、OAuth 等实现细节；只说明对用户有意义的行为。

验收：用户能从首页说明产品服务谁、帮助做什么，并通过一个明确主按钮进入工具。

## 4. 低门槛输入与兴趣分流

### FR-02 自然语言与可选简历（P0；对应 BR-02）

最低输入为一段兴趣、一个领域或明确的教授／实验室名称。用户也可以仅上传简历，再确认系统提取的兴趣候选；不能把简历中的每项经历直接当作当前意向。

| 信息 | 是否必填 | 用途与行为 |
|---|---|---|
| 兴趣／想了解的问题／已知对象 | 与简历至少提供一种有效输入 | 决定检索和展示方式 |
| 简历 | 否 | 提取专业、年级、课程和经历，供用户修正 |
| 专业、年级 | 否 | 解释背景，不自动限制院系 |
| 已有科研经验 | 否 | 调整解释深度，不作为入场门槛 |
| 时间、开始日期、持续时长 | 否 | 用户主动需要时用于公开条件比较 |
| 薪酬、学分偏好 | 否 | 搜索后筛选或排序偏好 |
| 技能、GPA、成绩单 | 否；不默认索要 GPA 或成绩单 | 仅在用户主动提供、具体申请明确需要时使用 |

上传后显示可编辑的简短提取结果。未知字段保持空白，不推测年级、能力或经历。文件无法读取时保留原始输入，允许粘贴简历文字或继续仅按兴趣探索；扫描件 OCR 不作为首版必须能力。

“用于推荐分析”与“作为邮件附件”是不同选择。上传简历不代表同意给每位教授发送简历。

### FR-03 自适应结果组织（P0；对应 BR-02、BR-03）

| 输入类型 | 第一屏 | 必须支持的后续行为 |
|---|---|---|
| 模糊兴趣，如“AI” | 少量通俗方向，每组有具体问题和代表教授 | 点选方向、同时选多个、先看全部、修改兴趣 |
| 单一明确方向 | 直接展示相关教授与实验室 | 可调整方向、查看相邻研究、修改条件 |
| 多个兴趣 | 按用户表达的兴趣并列展示，标明交叉 | 分别探索；可主动切换“同时相关” |
| 简历但无明确兴趣 | 展示推测的兴趣候选并允许确认或改写 | 不自动把履历限定为唯一方向 |
| 教授／实验室名称 | 优先查找并核实该对象 | 同名时提供院系等消歧信息 |

方向卡片必须包含：易懂标题、简短解释、一个研究问题或情景、专业关键词、可进入的代表对象。不能只给术语标签。

多个兴趣默认按“与任一兴趣相关”探索，不擅自采用交集；同一教授可以属于多个兴趣组，但收藏和联系时必须去重。Agent 与机器学习等重叠概念，不需要强行划成互斥分类。

系统在结果页用一行显示当前理解，例如“正在探索：AI Agent；范围：UW 全校”。用户能直接修改。系统不确定输入含义时先给合理的可编辑解释，不用长问卷阻断搜索。

## 5. 检索范围、证据与推荐规则

### FR-04 全校检索与身份核查（P0；对应 BR-03、BR-04）

搜索目标覆盖 UW–Madison 校内教授、实验室、明确公开的研究项目和本科研究申请入口。不硬编码只查少数院系；根据兴趣跨院系寻找关联。

优先来源：

1. 学校、院系和正式项目目录，用于确认当前归属。
2. 教授和实验室官网、明确公开的参与或申请页面。
3. 经校内目录或官网关联确认的外部个人网站。
4. 论文、项目材料等，用于补充研究内容；论文作者身份不能直接等同于当前校内 faculty。

处理要求：

- 不因个人网站使用 GitHub Pages 等外部域名就排除，但应核实对应身份。
- 同名教授、共同指导、多个实验室归属应消歧；过往成员不能自动当作当前导师。
- 校外合作者可作为研究内容背景，不混入本校导师名单。
- 检索失败、访问失败、找不到相关资料时分别说明，不编造结果填满页面。
- “全校”是搜索范围，不能显示“已经扫描全部教授”或未经证明的总覆盖百分比。
- 可复用已核实资料，必要时补充检索；缓存日期与网页原始更新时间分别记录。
- 用户可直接搜索姓名或实验室，结果不足时可扩大关键词或移除筛选；扩大行为应可见。

### FR-05 逐项证据与三态标签（P0；对应 BR-04）

#### 条件值

| 显示值 | 含义 | 不允许的推断 |
|---|---|---|
| 支持 | 公开来源明确支持该条件，且适用于当前对象和人群 | 不能由“有本科生成员”推出“正在接收本科生” |
| 不支持 | 公开来源明确排除该条件 | 不能由“没找到说明”推断为不支持 |
| 未说明 | 没有足够公开依据确定支持或不支持 | 不能显示成默认满足或默认不满足 |

适用条件包括本科生参与、学分、薪酬、远程等；仅展示有实际用途的条件。工时、期限等有明确值时保留数值和适用范围，没有值则不填写。

招募状态使用语义明确的状态：**开放申请／暂无空缺／未说明**。开放申请表示可提交申请或询问，不保证可用名额；长期申请表也不能自动等同于当季招募。

#### 证据状态

每条用于决策的事实保存：来源链接、对应文本或位置、适用对象、核查时间；网页存在更新时间时另行保存。

访问失败、资料过时或来源冲突时，相关字段按“未说明”处理并提供“暂无法核实／资料冲突”的说明，不冒充“已阅读官网且官网没有写”。有历史明确证据时可展示历史值，但必须标出历史状态，不用作当前确定性筛选。

网页今天被抓取，不意味着教授今天重新确认过招募状态。动态信息应有可见的“上次核查”日期。

#### 信息层次

| 内容类型 | 展示要求 |
|---|---|
| 原始事实 | 直接支持它的来源，如研究主题、申请表、邮箱 |
| AI 通俗解释 | 忠实于已获取材料，不扩大到没有依据的方法或成果 |
| 帮助理解的类比 | 明确是解释性例子，不当作该实验室真实项目 |
| 推荐理由 | 联系用户表达与已核实主题，写明推理关系 |
| 用户自己的想法或经历 | 由用户提供或确认，不能冒充官网事实 |

只有题目或摘要时，只能基于相应内容解释，不能写成已经完整分析论文或代码。

### FR-06 推荐与排序（P0；对应 BR-03、BR-04）

排序考虑研究相关性、材料能否支持解释、用户明确偏好及公开参与渠道。默认不按名气、论文数或学校排名排序，不以模型生成的录取概率作为推荐依据。

- 用户兴趣优先；专业和过往经历用于辅助解释。
- 允许推荐不同院系中与兴趣相关的研究，需说明相关性，而非仅包含相同关键词。
- 明确暂无空缺的对象降低“立即联系”优先级，但仍可作为研究探索对象查看和收藏。
- 未说明名额的对象可以推荐为“值得了解”，不写成“正在招人”。
- 只有公开明示的硬性限制，才可作为相应条件判断依据；若展示限制，必须说明来源和适用人群。
- 默认保留未知信息。用户主动选择“仅显示明确支持学分”时可排除未说明，同时显示被排除的未说明数量。
- 结果变化应能解释，例如“只看明确支持学分的结果”。不得悄悄改变原始兴趣。

## 6. 结果列表、研究详情与比较

### FR-07 结果列表和筛选（P0；对应 BR-04、BR-05）

单个列表条目至少包含：

- 教授／实验室名称、经核实的院系与关系。
- 一句话通俗研究介绍。
- 1–2 条与用户输入直接相关的推荐理由。
- 少量关键标签，如招募状态、学分说明。
- “了解研究”“查看主页”“收藏／加入比较”等动作。

筛选置于结果页，优先展示研究方向、院系和招募状态；学分、薪酬等放在可展开的更多条件中。用户不必先选筛选才能看结果。

公开记录不足时不显示“最适合你的前六名”；使用“值得进一步了解的研究”等准确表述。不让未经支持的“匹配分数”替代解释。

### FR-08 教授／实验室详情（P0；对应 BR-04、BR-06）

内容分层，默认先显示有助于理解和选择的内容，深入材料按需展开：

| 模块 | 必须回答的问题 |
|---|---|
| 基本信息 | 谁、当前属于哪里、与哪个实验室有关 |
| 一句话理解 | 这个研究大致在解决什么问题 |
| 具体研究问题 | 研究者到底想弄清楚什么 |
| 易懂例子 | 学生可以怎样理解；例子是真实项目还是解释性类比 |
| 常见研究方式 | 公开材料能确认的研究方法；未知就不编造 |
| 与我的联系 | 哪些兴趣相关，哪些只是相邻方向 |
| 代表材料 | 建议 1–2 个最有助于理解的项目／论文，带来源与摘要级别说明 |
| 参与条件 | 三态标签、明确要求和未知项 |
| 下一步 | 邮件、表单、项目申请或进一步了解；附可用入口 |

原始主页始终容易找到，在新标签页打开并保留当前选择。来源展开显示原文依据和核查时间。个别资料缺失不使整个页面不可用。

### FR-09 收藏与比较（P0；对应 BR-05）

收藏记录教授／实验室、相关兴趣、来源快照和可选个人备注。收藏不代表准备发送邮件；取消收藏不删除历史联系记录。

比较采用统一维度：研究问题、研究方式、与我的联系、公开参与条件、未知信息、下一步。各列采用相同语义和近似信息密度，未知项显示未知，不能以空白误导。

用户可从比较中返回详情或保留候选，不要求完成比较才允许联系。同一教授的多个研究方向可在一个对象内查看，联系名单按身份与邮箱去重；同实验室不同人员不自动视为同一人，但应提示共同实验室关系。

### FR-10 下一步行动分流（P0；对应 BR-06）

| 公开情况 | 默认主动作 | 处理要求 |
|---|---|---|
| 明确邮件联系 | 准备邮件 | 核实联系人和邮箱；可能是 PI 或明确指定的其他联系人 |
| 先填表再联系 | 查看申请表 | 说明顺序；不默认把它加入普通 cold email 批次 |
| 正式项目申请 | 查看申请与截止信息 | 保留原始申请入口；没有截止日期则未说明 |
| 明确暂无空缺 | 收藏／查看研究 | 不默认加入立即申请名单 |
| 只有公开邮箱，未说明参与方式 | 准备询问邮件 | 写明是在询问方式，不冒充已有开放职位 |
| 没有可核实邮箱或入口 | 查看主页／待核实 | 不猜测邮箱，不生成看似可发送的虚构地址 |

原始网页的博士招生指引不能套用到本科生。打开表单不等于已经申请；只有用户手动标记或可靠回执才能更新申请进度，首版不自动提交表单。

## 7. 邮件生成、编辑与个性化

### FR-11 快速批量生成（P0；对应 BR-07）

用户从候选中选择一个或多个适合邮件联系的对象，点击“一键生成草稿”。生成的是多封独立邮件，每封使用共同的真实背景和对应对象的研究内容。

默认结构：称呼、学生身份、对该研究的兴趣、已知背景或首次探索状态、明确请求、简短结尾。姓名、年级等未知时留可编辑位置，不自行补全。准备发送前应解决正文中的未填占位内容。

需要做到：

- 教授姓名、研究内容和邮箱来自正确对象，不能因批量生成串位。
- 同一背景信息只填一次，对不同实验室的兴趣分别组织。
- 不写未经确认的“读过论文”“复现方法”“有丰富经验”等表述。
- 有个人兴趣描述时优先使用；没有细节时诚实表达初步探索。
- 单封生成失败不清空成功草稿；失败对象可单独重试。
- 再次生成不得无提示覆盖用户手动修改；可以保留版本或先显示替换预览。

### FR-12 可选短问题个性化（P0；对应 BR-07）

每封草稿提供“补充细节”。优先用三个可跳过的短问题，支持点击选项、短文本和 AI 表达示例。

| 问题 | 候选内容 | AI 可以做什么 | AI 不能做什么 |
|---|---|---|---|
| 哪部分研究吸引你 | 从当前已解释且有来源的研究问题中选择；也可“还在探索” | 解释选项、提供兴趣表达范例 | 替用户断言已读论文或理解某项技术 |
| 想提及什么经历 | 用户确认的简历条目、课程、个人项目、没有相关经历 | 整理短语、保持事实、改善语言 | 编造课程、项目、成绩或能力 |
| 希望这次联系得到什么 | 询问机会、参与流程、研究方向或准备建议 | 结合公开申请方式组织请求 | 假定已获面试或已有职位 |

AI 范例与用户确认的内容分开。点击查看范例不等于确认经历真实；选定或编辑后才将其作为个人内容。经历选项只能来自用户资料或用户明确补充，不能用默认勾选制造经历。

共同信息可以复用；教授相关兴趣不自动套用到所有邮件。个性化保持可选，用户可先批量生成，再只完善少数重点对象。

### FR-13 草稿、附件与最终预览（P0；对应 BR-07、BR-08）

邮件工作区支持切换对象、编辑收件人／主题／正文、查看个人化内容和来源。用户手动修改收件人时保留“用户填写”来源标识，检查基本格式，不伪称已由官网核实。

附件要求：

- 默认不因为上传过简历就自动附加。
- 用户可选择将确认过的同一份简历附加到若干邮件，并逐封查看附件名和大小。
- 发送预览中出现的附件，必须是实际发送的版本；更换文件后旧批次不得悄悄改变。
- 生成“见附件”等语句前确认存在附件；用户移除附件后提示检查相关文字。

发送预览集中展示每封邮件的收件人、主题、正文、附件、已选状态和申请渠道提示。用户可检查所有草稿后一次确认所选批次，不要求逐封重复确认；默认不得将未生成成功或缺少收件人的草稿混入批次。

## 8. 邮箱连接与真实批量发送

### FR-14 用户邮箱连接（P0；对应 BR-08）

发送前通过邮箱提供方的正常登录授权流程连接用户本人邮箱。仅填写邮箱地址不产生发送权限。产品不索取或保存用户邮箱密码，不从项目公共邮箱伪装成学生发信。

探索、比较和草稿生成无需提前连接邮箱。建议第一版优先 Microsoft 365，因为这是 UW 学校邮箱服务；是否可用需要实际验证。[S1]

授权界面和产品提示应明确：当前连接的是哪个账户，应用将发送用户确认的邮件。发送能力本身不要求把读取整个收件箱作为产品前置条件；如实现方案需要其他权限，必须明确其用途与最小范围。

取消、拒绝或过期时保留工作区和草稿；学校要求管理员批准时显示真实原因和可继续保存的内容，不要求用户不断重试。学校是否允许此应用接入仍是未完成的可行性验证，不在本 PRD 中假定成功。[S2]

断开邮箱后不能继续发送。重新连接后恢复待处理内容，但不能自动发送上一次未完成的批次。

### FR-15 批次与发送状态（P0；对应 BR-08）

用户在预览页确认“发送所选 N 封”后，系统固定本次收件人、主题、正文和附件版本，为每封邮件建立独立记录，再按提供方允许的速率发送。

不使用同一封邮件的多人 To／Cc／Bcc 模拟个性化群发。实际发件人必须是已连接账户，发件人身份应在确认前可见。

| 状态 | 含义 | 允许的后续操作 |
|---|---|---|
| 草稿 | 尚未加入确认后的批次 | 编辑、删除、加入预览 |
| 排队中 | 用户已确认，尚未提交邮箱服务 | 可取消未提交项 |
| 提交中 | 正在与邮箱服务交互 | 不重复点击提交 |
| 已提交邮箱服务 | 提供方已接受请求 | 查看记录；不得当作失败项自动重发 |
| 发送失败 | 已收到明确失败且确认没有完成提交的结果 | 说明原因；修正后仅重试该项 |
| 状态待核实 | 超时或断线，无法确认是否已被接受 | 核对记录或用户确认后处理，不盲目重发 |
| 已取消 | 还未提交的队列项被取消 | 可重新准备新的批次 |

Microsoft Graph 的 `202 Accepted` 表示接受请求，不等于投递完成。因此首版默认显示“已提交邮箱服务”，不能伪称教授已收到、已读或已回复。[S3]

可靠性要求：

- 重复点击、刷新、重新进入和网络重试不能创建同一项的重复发送。
- 本地批次／消息标识用于去重和追踪，不能据此声称外部邮箱接口具有完全一次的提交保证。
- 部分成功时逐封显示结果，不因为一封失败重发整个批次。
- 凭证中途过期时停止剩余未提交项；重新连接不重发已接受项。
- 对确定失败项提供单独或批量重试；未知状态先核对。
- 发送后保留当时正文与附件信息；后续编辑产生新草稿，不改写历史记录。
- 批次上限、间隔和配额由服务限制与测试确定，并在确认前告知；不静默丢弃超额项。
- 第一版不自动追加新收件人，不自动发送跟进邮件。

如果真实发送受外部授权阻断，复制或导出草稿可作为临时保留方式，但不算 FR-15 验收通过。演示模式必须明确标注模拟，不产生真实状态记录。

### FR-16 保存与联系记录（P0；对应 BR-05、BR-08）

至少在当前浏览器保留搜索上下文、收藏、比较对象、确认的背景、草稿与联系记录。正常刷新、返回列表、授权跳转回来后，不丢失已保存的内容。

访客模式应说明保存范围；清理浏览器数据可能影响本地记录。跨设备账户同步可后续扩展，不能在没有实现时承诺。

联系记录区分自动记录的发送状态和用户手动填写的进度，例如“已填写表单”“收到回复”。首版不读取收件箱时，不能自动宣称无回复或推断拒绝。用户自行查看邮箱中的回复。

## 9. 完整用户案例

本节用于确认交互，所有字母教授和实验室条件均为假设，不是实际 UW 推荐数据，也不能直接放入正式检索结果。

### 9.1 主案例：兴趣模糊、没有简历、第一次找科研

人物：Alex，UW 大二 CS 本科生，没有科研经历，只知道自己对 AI 感兴趣。

| 步骤 | 用户看到／做什么 | 系统行为 | 用户获得的判断 |
|---|---|---|---|
| 1 首页 | 看到用途与简短预览，点击 Get Started | 进入工具，不强制注册或连接邮箱 | 知道这是找研究、理解研究和联系的工具 |
| 2 输入 | 输入“我对 AI 感兴趣，想找第一段 research” | 无简历也能开始；保留原文 | 不需要先整理完整技能清单 |
| 3 方向 | 看到 AI Agent、AI 与学习、机器人学习的通俗问题及代表对象 | 方向不是互斥门类；可切换 | 发现自己更关心 AI 如何影响学习 |
| 4 筛选 | 点“AI 与学习” | 跨计算机、教育、心理相关院系寻找；显示本次已找到的对象 | 兴趣比所属院系更重要 |
| 5 列表 | 看到 A 的学习工具研究、B 的学习行为研究、C 的人机交互研究、D 的相关但暂无空缺状态 | 每个条目有一句话、理由与公开条件 | 选择 A、B、C 继续了解 |
| 6 详情 | 打开 A；看通俗解释、具体问题、例子和原网页 | 真实项目与解释性类比分开；学分未说明就保持未知 | 理解 A 做什么，能说出兴趣所在 |
| 7 比较 | 将 A 与 C 并排比较；B 的下一步为申请表 | 同维度比较，突出方法与参与渠道的区别 | 确定联系 A、C，另行查看 B 的表单 |
| 8 快速草稿 | 选 A、C 批量生成邮件 | 分别生成内容；没有经历不造经历 | 两封可编辑的初稿 |
| 9 个性化 | 对 A 选择感兴趣的问题、没有相关经历、询问参与方式 | 只更新 A；C 保留快速草稿；不替用户声称读过论文 | 重点邮件表达个人真实兴趣 |
| 10 预览 | 检查 A、C 的收件人、正文、附件；确认选择 | 两封独立邮件；B 不混进邮件批次；未上传附件则不写见附件 | 知道将发送什么、给谁 |
| 11 连接 | 点击连接学校邮箱，完成提供方授权 | 回到原预览页，保留草稿；授权失败则解释并保留 | 明白发送使用自己的账户 |
| 12 发送 | 一次确认发送两封 | 独立提交并记录结果；不重复发送 | 知道哪些已提交、哪些仍需处理 |
| 13 后续 | 回看已联系对象与原始资料；可手动记下 B 的申请情况 | 保存历史内容，不把打开表单当作申请完成 | 下次无需重新整理全过程 |

### 9.2 方向明确、有简历

用户明确写“想探索 LLM agent 的规划”，同时上传主要是网页开发经历的简历。系统直接展示 agent 相关对象，简历只辅助说明背景。不能强迫用户再次选择所有 AI 大类，也不能因为过去经历而改推网页开发教授。

### 9.3 多个兴趣

用户同时选择 agent 和机器学习。系统按兴趣展示，可标记交叉对象。默认保留任一方向相关的结果；只有用户主动选择“同时相关”才采用交集。教授可能在两个方向中出现，但最终联系记录只对应一个确定的人和收件地址。

### 9.4 信息不足与发送异常

来源未说明学分时显示未说明，不能为了满足用户偏好改写为支持。网页打不开时说明暂无法核实，并允许继续看其他可靠内容。

假设两封邮件一封收到接受响应、一封连接中断：前者记为已提交，后者记为待核实；不显示“全部失败”后重发两封。若学校授权被拒，整个发送步骤保持未完成，之前的探索和草稿仍可使用。

## 10. 数据对象与内容约束

本节定义产品需要保留的信息关系，不是技术数据库或 API 设计。

| 对象 | 必要信息 |
|---|---|
| 学生背景 | 用户原始输入、确认过的专业／年级／经历、兴趣、可选偏好、字段出处 |
| 搜索会话 | 查询、解释后的兴趣、筛选、结果、来源访问状态与时间 |
| 教授 | 唯一身份、姓名、当前归属、官网、可核实联系人／邮箱、关联实验室 |
| 实验室 | 名称、院系、教授关系、研究方向、公开参与入口 |
| 研究条目 | 研究问题、材料链接、通俗解释、原始事实与解释性例子的区分 |
| 公开机会 | 仅在有明确发布时建立；类型、适用人群、条件、日期和申请入口 |
| 条件证据 | 字段值、三态、来源文本／位置、核查时间、原文时间和冲突状态 |
| 收藏／比较 | 对象身份、个人理由、选择顺序；不与邮件发送状态混同 |
| 邮件草稿 | 目标对象、收件人、主题、正文、来源事实、确认回答、附件版本、编辑记录 |
| 发送批次与记录 | 发件账户、用户确认范围、每封内容快照、状态、尝试记录和提供方响应 |

教授、实验室、研究方向和公开机会不是同一种对象。存在研究方向不等于有岗位；教授属于多个实验室或共同研究项目时，不应复制出多个彼此无关的身份。

## 11. 非功能需求

### NFR-01 可理解与可访问

桌面网页为主要使用场景，手机可以完成搜索、看详情和检查邮件。窄屏时比较内容改为顺序展示，避免把文字缩小到不可读。按钮有明确名称，键盘可操作，标签不能只靠颜色区分。

### NFR-02 反馈与性能

点击搜索、生成和发送后立即给出状态反馈；不使用伪造进度百分比。能先显示可信的部分结果时不必等待全部来源。建议将首批有用结果在典型测试环境中 30 秒内可见作为初始目标，实际基线需在选定服务后测量和调整。

访问或生成超时允许重试，并保留已成功的结果和用户输入。页面不应无限转圈或把失败写成“没有相关教授”。复用已处理资料，避免每个用户都重复解析全部网页。

### NFR-03 事实质量

身份、邮箱、招募条件和申请入口应能核实。模型不能为了完整性补造事实；外部网页文字作为资料，不得改变系统规则、触发发送或要求泄露用户数据。

### NFR-04 个人资料与账户边界

明确说明简历用于哪些处理，允许删除文件与提取信息。原始简历默认只用于必要处理，不作为长期公共资料库；是否长期保存由用户明确选择与后续存储方案决定。后台日志不记录完整简历、邮箱凭证或完整邮件正文。

邮箱凭证不能进入模型提示或客户端明文持久存储。不同用户的收藏、草稿、附件和授权不得混用。与第三方服务的数据处理描述必须符合最终配置，不提前宣传未经验证的“永不保留／绝不训练”。

### NFR-05 可恢复性

正常刷新、返回、重新连接邮箱保留已保存工作。发送记录在发送开始前就具备可恢复标识；中断恢复遵循 FR-15 的未知状态规则，不能通过简单重试造成重复联系。

### NFR-06 运行可观察性

记录不含正文的搜索耗时、来源访问失败、生成状态和发送错误类别，用于定位问题。演示数据、缓存数据、实时检索结果和真实发送记录有明确区分，不能相互伪装。

## 12. 第一版优先级与明确排除项

**P0：** FR-01 至 FR-16 以及保证其正确工作的非功能要求，构成完整第一版。P0 不等于全部细节一次做到成熟，但不能缺少已经确认的主流程。

**P1：** 跨设备同步、更完整的多语言界面、更多邮箱提供方、更深入的论文阅读辅助、用户主动设置的机会更新提醒。

**不在当前范围：** 教授端招聘平台、非公开名额推测、强制技能测评／科研试做、自动填表申请、自动跟进催信、完整收件箱或 CRM、外校推荐、自动发信给未选中的对象。

如果时间不足，先削减 P1 和装饰性功能；不能静默将批量发送降级为复制草稿，或将全校探索变成只有少量预置假数据的列表。

## 13. 验收用例

以下用例用于后续开发验收；本文没有声称这些测试已经运行。

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC-01 | 首页 Get Started | 一次进入工具，未被长表或邮箱授权阻断 |
| AC-02 | 只输入“AI”，无简历 | 返回易懂方向和代表对象，能继续细化 |
| AC-03 | 明确 agent 方向 | 直接给相关对象，不强制重走宽泛方向选择 |
| AC-04 | 两个交叉兴趣 | 默认任一相关，交叉可见；收藏和邮件对象去重 |
| AC-05 | 简历经历与意向不同 | 明确意向优先，不把技能当作硬门槛 |
| AC-06 | 简历损坏或扫描不可读 | 提示具体问题，能改用文本或无简历继续 |
| AC-07 | 跨院系检索 | 同一兴趣能发现有依据的不同院系对象，未承诺穷尽全校 |
| AC-08 | 来源未写学分 | 显示未说明；默认不过滤；严格支持筛选时解释排除 |
| AC-09 | 来源冲突或不可访问 | 不显示无依据的确定结论，有核查状态说明 |
| AC-10 | 通俗解释与项目 | 不改变原研究含义；类比与真实项目区分；有直接来源 |
| AC-11 | 原始主页与返回 | 原网页可打开，原选择与筛选不会丢失 |
| AC-12 | 比较两个候选 | 同维度呈现；未知不留成误导性空白；能返回详情 |
| AC-13 | 表单、邮件、暂无空缺 | 主动作正确；不将博士指引当本科指引；不能仅打开表单就标记申请完成 |
| AC-14 | 快速生成多个草稿 | 每封对应正确姓名、研究和邮箱；单封失败可独立处理 |
| AC-15 | 没经历且未读论文 | 草稿不虚构经历或阅读行为；无需填写不存在的技能 |
| AC-16 | 查看 AI 范例后跳过 | 未确认的个人事实不自动加入邮件 |
| AC-17 | 只完善一封邮件 | 更新目标草稿，其他草稿与手工修改保持完整 |
| AC-18 | 附件选择与变更 | 预览与真实提交的版本一致，未选择就不自动附加 |
| AC-19 | 邮箱取消／拒绝／过期 | 草稿不丢失，不能伪称已经授权或已经发送 |
| AC-20 | 授权后批量发送 | 在获授权的团队测试账户验证每人一封、内容各自对应 |
| AC-21 | 两封部分成功 | 分别显示接受／失败或待核实，不重发成功项 |
| AC-22 | 连点、刷新、网络中断 | 无意外重复发送；无法确认时待核实，不伪造成功 |
| AC-23 | 服务返回 202 | 显示接受请求，不宣称送达、已读或回复 |
| AC-24 | 返回／刷新／授权跳转 | 保存过的查询、候选和草稿可恢复；账户之间不串数据 |
| AC-25 | 模拟演示 | 明确虚构资料与模拟发送；与真实记录隔离 |
| AC-26 | 手机与键盘 | 主要流程可操作、无关键内容被遮挡，状态有文字说明 |

抽查建议覆盖三种输入、跨院系关系、三态条件、表单入口、暂无空缺和一组真实邮件发送测试。真实邮箱测试只使用团队控制且获得授权的账户，不能为测试向真实教授发信。

## 14. 开发前验证项与实施顺序

| 编号 | 问题 | 需要的证据 | 对第一版的影响 |
|---|---|---|---|
| V-01 | UW 邮箱能否给本应用授权发送 | 应用注册、本人授权、团队测试收件箱中的实际结果 | 是真实批量发送的关键依赖 |
| V-02 | 全校跨领域检索是否能形成可靠候选 | 不同学科与跨学科查询的来源样本、漏项和失败记录 | 决定覆盖说明、检索策略与成本 |
| V-03 | 通俗解释是否准确且能看懂 | 原资料对照和首次找科研学生的复述反馈 | 决定产品核心价值是否成立 |
| V-04 | 最小输入是否足以开始 | 无简历、模糊兴趣的实际用户流程 | 防止不断增加必填问题 |
| V-05 | 授权、刷新与重试能否恢复 | 草稿、批次和未知发送状态的验证 | 防止遗漏与重复发送 |
| V-06 | 服务成本与等待时间 | 选定服务后的真实测量 | 决定缓存、批量限制和可见反馈 |

建议顺序：先确认关键页面和上述可行性，再确定技术方案；实现时先打通一条真实端到端流程，再扩展查询与来源覆盖。不得先堆很多假教授页面，再把来源质量与邮件授权留到最后。

本次仅交付需求文档。截至本版，尚未进行应用开发、注册邮箱应用、连接用户账户、真实检索管线建设或邮件发送。
